# 鳴潮相關資料參考

本文件整理把原神祈願卡池分析（Genshin Impact Wish Gacha Analyzer）改造為鳴潮喚取卡池分析所需的全部背景資料，供後續修改程式碼時對照參考。

- 「鳴潮」英文名稱為「Wuthering Waves」。
- 開發商：庫洛遊戲（Kuro Games）。
- 本專案沿用原神版「本機代理伺服器 + 自簽根憑證攔截」架構，但鳴潮的喚取記錄取得方式與原神差異甚大，詳見下方各節與〈與原神版的對照〉。
- 範圍決策：**僅支援國際服**（`svr_area=global`，`*.aki-game2.net`），暫不支援國服，與原神版一致。

## 一、喚取記錄取得流程

玩家在遊戲內開啟「喚取 →（畫面右下）喚取記錄」時，會載入一個 WebView 頁面，該頁面隨即向後端 API 發出 POST 請求拉取記錄。本軟體沿用原神版「本機代理 + 自簽根憑證」的攔截架構，攔的就是這條 POST。

### 攔截規則

代理一律偵測符合以下條件的請求並取其 **POST body**：

```
POST https://gmserver-api.aki-game2.net/gacha/record/query
```

- 比對條件：host = `gmserver-api.aki-game2.net` 且 path = `/gacha/record/query`（國際服）。
- 攔到後直接讀請求 **body**（JSON），裡面已含查詢喚取記錄所需的全部憑證：`playerId` / `cardPoolId` / `serverId` / `recordId` / `languageCode`（欄位詳見〈二、API 規格〉）。
- 取得這份 body 後，本軟體即可自行用相同憑證、迭代 `cardPoolType` 重打此 API 拉齊各卡池記錄，不需玩家在遊戲內逐一切換卡池。

> 與原神版的差異：原神攔的是 **GET**、參數在 URL query；鳴潮攔的是 **POST**、憑證在請求 **body**。`rust/src/mitm.rs` 的比對與擷取邏輯需據此改寫。

## 二、喚取記錄 API 規格

### 端點

```
POST https://gmserver-api.aki-game2.net/gacha/record/query
```

- 國際服：`gmserver-api.aki-game2.net`。
- 國服（暫不支援）：`gmserver-api.aki-game.net`。
- `Content-Type: application/json`。
- **攔截規則**：代理一律偵測 host = `gmserver-api.aki-game2.net` 且 path = `/gacha/record/query` 的請求，攔下後直接取其 **POST body** 作為查詢憑證（body 內已含完整 `playerId` / `cardPoolId` / `serverId` / `recordId` / `languageCode`）。

### 請求 body（JSON）

以下為實際攔到的角色活動喚取（`cardPoolType: 1`）請求範例：

```json
{
  "playerId":     "701******",
  "cardPoolId":   "2e23************************2768",
  "cardPoolType": 1,
  "serverId":     "86d5************************9650",
  "languageCode": "zh-Hant",
  "recordId":     "0632************************8550"
}
```

| body 欄位        | 型別     | 說明                                            |
|----------------|--------|-----------------------------------------------|
| `playerId`     | string | 玩家 UID（即遊戲內顯示的特徵碼）                          |
| `cardPoolId`   | string | 卡池資源版本 hash，**所有卡池型別共用同一值**               |
| `cardPoolType` | int    | 卡池類型，需由程式**逐一迭代**查詢（見下方說明）               |
| `serverId`     | string | 伺服器 ID hash，**逐帳號不同、由攔到的 body 取得**         |
| `languageCode` | string | 語言（例：`zh-Hant`），決定回應內名稱/類型字串的語言           |
| `recordId`     | string | 查詢 token hash，**會過期，過期後需請玩家重開喚取記錄頁重新攔取** |

- `cardPoolType` 需由程式**逐一迭代固定集合 `[1, 2, 3, 4, 5, 6, 8, 9]`**（見〈卡池類型〉，**注意沒有 7**）：攔到的 body 只帶玩家當下開啟的那一個卡池，要拿其他卡池就用相同 `playerId` / `serverId` / `recordId` / `cardPoolId`、只替換 `cardPoolType` 重發。
- `cardPoolId` 在**所有卡池型別共用同一個值**（已由 8 種型別的實際 body 佐證皆為同一 hash），為每帳號/每次擷取的固定值，與 `cardPoolType` 無關，迭代時不需更動。

### 回應 schema（JSON）

以下為實際回應範例（角色活動喚取，節錄不同稀有度/類型各一筆）：

```json
{
  "code": 0,
  "message": "success",
  "data": [
    {
      "cardPoolType": "1",
      "resourceId":   1211,
      "qualityLevel": 5,
      "resourceType": "角色",
      "name":         "達妮婭",
      "count":        1,
      "time":         "2026-05-21 10:39:03"
    },
    {
      "cardPoolType": "1",
      "resourceId":   1601,
      "qualityLevel": 4,
      "resourceType": "角色",
      "name":         "桃祈",
      "count":        1,
      "time":         "2026-05-21 11:03:18"
    },
    {
      "cardPoolType": "1",
      "resourceId":   21010024,
      "qualityLevel": 4,
      "resourceType": "武器",
      "name":         "異響空靈",
      "count":        1,
      "time":         "2026-05-21 11:02:16"
    },
    {
      "cardPoolType": "1",
      "resourceId":   21040084,
      "qualityLevel": 4,
      "resourceType": "道具",
      "name":         "塵雲旋臂",
      "count":        1,
      "time":         "2026-02-07 16:19:41"
    },
    {
      "cardPoolType": "1",
      "resourceId":   21020023,
      "qualityLevel": 3,
      "resourceType": "武器",
      "name":         "源能迅刀·測貳",
      "count":        1,
      "time":         "2026-05-21 11:03:18"
    }
  ]
}
```

| 欄位             | 型別     | 說明                                                | 對應原神欄位          |
|----------------|--------|---------------------------------------------------|----------------|
| `code`         | int    | 0 = 成功；非 0 = 失敗（已知 `-1`，見下方錯誤處理）              | `retcode`      |
| `message`      | string | 狀態訊息（例：`success`）                                | `message`      |
| `data[]`       | array  | 該 `cardPoolType` 的**全部**記錄（依時間由新到舊）              | `data.list`    |
| `cardPoolType` | string | 卡池類型（**字串**，與查詢的 int 對應，回應內每筆都帶）                | `gacha_type`   |
| `resourceId`   | int    | 道具資源 ID（可用於對應圖片）                                  | —（原神靠名稱對 wiki） |
| `qualityLevel` | int    | 稀有度（觀測只有 5 / 4 / 3，**鳴潮喚取無 1★/2★**）              | `rank_type`    |
| `resourceType` | string | 道具類型（觀測值：`角色` / `武器` / `道具`，字串隨 `languageCode` 變化） | `item_type`    |
| `name`         | string | 道具名稱                                              | `name`         |
| `count`        | int    | 數量（通常為 1）                                         | —              |
| `time`         | string | 抽取時間（伺服器在地時間字串，格式 `YYYY-MM-DD HH:mm:ss`）        | `time`         |

> 注意（皆由實際 type 1 全歷史資料佐證）：
> - **同一卡池型別會混入多種 `resourceType`**：角色活動池（type 1）除了「角色」，也大量出現「武器」（保底墊的 3★/4★ 武器）甚至「道具」（如 4★「塵雲旋臂」）。故稀有度與類型一律逐筆讀欄位，**不可用卡池型別推定**。
> - **單次回應是該「卡池型別」的全歷史**，跨多個活動 banner 合併在一起（範例中達妮婭、鑒心、愛彌斯、凌陽、維里奈是不同期 5★，全列在 type 1）。API **不提供逐 banner 細分**，保底要理解成「同型別跨 banner 連續累計」。
> - **`resourceId` 命名規律（供圖片對應參考）**：角色為 4 碼（如 `1211` 達妮婭、`1601` 桃祈）；武器/道具為 8 碼（如 `21020023`），其中 4★ 武器/道具倒數第二碼多為 `4` 或 `8`（如 `21010024`、`21030084`），3★ 多為 `3`。此規律待實作期作為 `resourceId` → 圖片對應的線索之一。

> ⚠️ **三個關鍵差異**：
> 1. **無分頁**：單次回應即回傳該卡池全部記錄，沒有 `end_id` / `page` / `size` 的分頁機制（原神版 `gacha_url.dart` 的 `build()`、`gacha_fetcher.dart` 的逐頁 + `end_id` 迴圈在此用不到）。
> 2. **無唯一 id**：每筆記錄沒有原神那種唯一流水號 `id`。
> 3. **同一十連 `time` 完全相同**：同一抽十連的多筆記錄時間戳一致（範例兩筆皆 `2026-05-21 11:03:18`），因此單靠 `time`、甚至 `time+name+qualityLevel` 複合鍵都可能在「同一批內抽到重複道具」時碰撞。
>
> **建議的合併策略**：API 每次都回傳該卡池由新到舊的**完整有序清單**，增量合併應改為**比對有序清單**——把新清單從頭（最新）往下吃，直到對齊到既有存檔的已知序列為止，而非靠單一 key 比大小（原神版 `_idGreater` / `existingMaxId` 的整段邏輯需重寫）。`resourceId` 可作為比對輔助，但仍無法區分同批同道具，務必以「清單順序」為準。

### 錯誤處理

已觀測到的失敗回應（例如 `recordId` 過期時出現，但不確定是否為過期專屬，可能是通用錯誤碼）：

```json
{
  "code": -1,
  "message": "请求游戏获取日志异常!",
  "data": []
}
```

- 判斷依據：**以 `code != 0` 視為失敗**，不要假設 `-1` 一定代表「過期」；`-1` 目前看來像是後端的通用錯誤碼，實際語意待累積更多樣本再細分。
- `message` 為**簡體中文**，與 `languageCode` 無關，不要用它判斷，請以 `code` 為準。
- 處理方式（對應原神版 `gacha_fetcher.dart` 的 `AuthExpiredException`，原神是 `retcode -100/-101`）：偵測到 `code != 0` 時中止本次更新，提示玩家「重新到遊戲開啟喚取記錄頁」以重新攔取新的 `recordId` 後重試，沿用原神版「網址過期請重開頁面」的 UX。由於無法區分過期 vs 其他錯誤，這個提示用通用措辭即可（「取得記錄失敗，請重開喚取記錄頁再試」）。

## 三、卡池類型（cardPoolType）對照

以下 8 種型別與 zh-Hant 名稱皆由實際攔截的 body 佐證（en／ja 名稱見 [術語表.md](術語表.md)）。**`cardPoolType` 的合法集合為 `[1, 2, 3, 4, 5, 6, 8, 9]`，沒有 7。**

下表保底數（5★ / 4★）皆已確認正確。

| cardPoolType | 名稱（zh-Hant）   | 5★ 保底 | 4★ 保底 | 備註             |
|--------------|---------------|-------|-------|----------------|
| 1            | 角色活動喚取        | 80    | 10    | UP 50/50       |
| 2            | 武器活動喚取        | 80    | 10    | 5★ 100% UP（無歪） |
| 3            | 角色常駐喚取        | 80    | 10    | 僅出 5★ 角色       |
| 4            | 武器常駐喚取        | 80    | 10    | 僅出 5★ 武器       |
| 5            | 新手喚取          | 50    | 10    | 50 抽必出 5★ 角色   |
| 6            | 新手自選喚取        | 80    | 10    | 新手後可自選常駐 5★    |
| 8            | 角色新旅喚取        | 80    | 10    | 角色池            |
| 9            | 武器新旅喚取        | 80    | 10    | 武器池            |

## 四、保底與機率規則

- **5★**：基礎機率 0.8%，最大保底 80 抽（軟保底約自第 66 抽起急遽提升），抽到即重置計數。
- **4★**：基礎機率 6%，最大保底 10 抽，抽到即重置計數。
- **角色活動喚取（type 1）**：5★ 為 50/50（歪了下一個 5★ 必為 UP）。
- **武器活動喚取（type 2）**：5★ 100% 為當期 UP 武器，無歪機制。
- **常駐喚取（type 3 / 4）**：角色池只出 5★ 角色、武器池只出 5★ 武器。
- **新手喚取（type 5）**：50 抽必得 5★ 角色，僅能十連、有折扣。

> 對照原神版 `gacha_types.dart` 的 `PityRule`：鳴潮 5★ 多為 80（非原神的 90/80/70 分歧）、4★ 統一 10，且沒有原神「頌願（odes）」這種雙 endpoint 概念，整體保底表會比原神單純。

### 保底計算基準（實作注意）

- 「距離保底剩餘抽數」「平均出貨抽數」依**該 `cardPoolType` 的全歷史、由 `qualityLevel` 計數**即可，保底是同型別跨 banner 連續累計（不重置於換期）。
- `resourceType` 為「道具」者**仍依其 `qualityLevel` 計入對應稀有度保底**（如 4★ 塵雲旋臂計入 4★）。
- **不追蹤 50/50（UP/歪）**：喚取 API 不提供每抽當期 UP 角色，無法判斷是否歪保底；此與原神版一致（原神版本來也未做 UP/歪判斷），維持只顯示保底距離與平均出貨，不新增 UP/歪相關功能。

## 五、圖片與資料來源

- **道具資料（名稱、稀有度、類型）**：直接取自喚取記錄 API 回應，**不需**像原神版額外打 HoYoWiki 補資料。
- **圖片來源（決策）**：走**官方攻略站 API**，且**只取圖片**（不抓描述、標籤等額外資料）。

### 官方攻略站圖片 API（角色）

```
GET https://guide-server.aki-game.net/introduction/list?roleGbId={resourceId}
```

- `roleGbId` 直接帶喚取記錄回應的 **`resourceId`**（角色為 4 碼，如達妮婭 `1211`）。
- **Header 必帶 `X-Language`**：其值必須**與攔到的 `/gacha/record/query` body 中的 `languageCode` 一致**（如 `zh-Hant`），確保圖片 API 回傳的文案語言與喚取記錄相同。
- 回傳取圖欄位：
  | 用途      | JSON 路徑                            |
  |---------|------------------------------------|
  | icon 小圖 | `data[0].role.cardPictureUrl`      |
  | 大圖（立繪）  | `data[0].role.illustrationPictureUrl` |

> **重要（只有角色有圖）**：官方僅攻略站提供圖片，且**只涵蓋角色**。因此 `resourceType` 為「武器」「道具」者（8 碼 `resourceId`）**一律沒有圖片來源**，不需嘗試抓取。UI 需自行處理「無圖」情境（顯示 placeholder／僅文字／依稀有度底色等），表格、時間軸、分享圖等所有用到 icon 的地方都要能容忍道具無圖。

## 七、術語對照

UI 與多語系的標準譯名一律以 [術語表.md](術語表.md) 為單一來源（含「喚取／Convene」、8 種喚取卡池名、「保底／pity」、「稀有度／Rarity」、「5★／4★／3★」等）。本節僅補充 doc／API 專屬、術語表未涵蓋的對照：

| 概念 / API 值              | 對照                                         |
|------------------------|--------------------------------------------|
| `cardPoolType`（API 欄位） | 卡池類型，值 `[1,2,3,4,5,6,8,9]`，名稱見〈三、卡池類型對照〉與術語表 |
| `qualityLevel`（API 欄位） | 稀有度（5 / 4 / 3）                              |
| `resourceType` 值       | `角色` / `武器` / `道具`                          |
| 「喚取記錄」                 | 遊戲內頁面名（對應原神「卡池歷史記錄」）                        |
